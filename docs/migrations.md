# Database migrations

## What changed

`PostgresOperationalStore.initialize()` still runs an idempotent
`CREATE TABLE IF NOT EXISTS` baseline on every startup (unchanged — tests and first-run
local/dev convenience depend on it). It has no column-evolution story, no ordering
guarantee across replicas racing to initialize, no downgrade path and no audit trail of
*which* schema version a given deployment is running. That is now a development/bootstrap
convenience, not the production migration path.

The production path is [Alembic](https://alembic.sqlalchemy.org/), configured in
`alembic.ini` / `migrations/`:

- `migrations/versions/0001_initial_schema.py` — the same schema `PostgresOperationalStore
  ._SCHEMA` documents, written idempotently so it is a safe no-op against a database an
  older deployment already bootstrapped via `initialize()`.
- `migrations/versions/0002_retention_indexes.py` — adds the indexes the automated
  retention purge job (`docs/data-retention.md`) needs to scan efficiently.
- Every later schema change is a new, reviewed, non-idempotent revision with a real
  `downgrade()`.

Alembic is used purely as a versioned-migration ledger (`alembic_version` table) and
executor; there is no SQLAlchemy ORM layer in this codebase, so every migration is
hand-written SQL via `op.execute(...)`, never autogenerated from models that don't exist.

## Running migrations

```bash
pip install -e ".[migrations]"
export ART_DATABASE_DSN="postgresql://user:pass@host/db"   # or let the script resolve
                                                             # it from the configured
                                                             # secret provider — see below
python scripts/run_migrations.py upgrade head
python scripts/run_migrations.py current
python scripts/run_migrations.py downgrade -1   # only against an isolated/disposable DB
```

`scripts/run_migrations.py` resolves the DSN the same way the API composition root does:
directly from `ART_DATABASE_DSN` if set, otherwise from the configured secret provider
(`ART_SECRET_PROVIDER` = `mounted` / `aws_secrets_manager` / `hashicorp_vault`, naming the
secret via `ART_DATABASE_DSN_SECRET_NAME`). No DSN or credential is ever logged.

## Automated in deployment

`deploy/helm/art-sim/templates/migration-job.yaml` runs `upgrade head` as a Helm
`pre-install,pre-upgrade` hook `Job` — it must complete before Helm proceeds to roll the
`Deployment`, so no API or worker pod ever starts against a schema it does not understand.
The hook Job uses the same hardened pod/container security context, image and mounted
secrets as the application `Deployment`. Set `migrations.enabled: false` in `values.yaml`
only for a deployment that manages migrations through an external pipeline step instead.

For `docker-compose.prod.yml` (non-Kubernetes) deployments, run
`python scripts/run_migrations.py upgrade head` as an explicit step in the deploy pipeline
before `docker compose up -d` recreates the `api`/`worker` services — see
`docs/deployment.md`.

## Authoring a new migration

```bash
alembic -c alembic.ini revision -m "add simulation_runs.priority"
```

Write `upgrade()`/`downgrade()` as plain `op.execute("ALTER TABLE ...")` statements. Every
migration must:

- be reviewed like any other schema change affecting a table under row-locking
  (`SELECT ... FOR UPDATE`) coordination — avoid long-running `ALTER TABLE` rewrites against
  a live table workers and the API are actively using;
- include a working `downgrade()` unless the change is explicitly irreversible (e.g. a data
  deletion), in which case the function must say so and fail loudly rather than silently
  no-op;
- be exercised against a real PostgreSQL instance before merge — `tests/integration
  /test_postgres_migrations.py` applies every revision to a throwaway schema and asserts
  `alembic_version` lands on the expected head.
