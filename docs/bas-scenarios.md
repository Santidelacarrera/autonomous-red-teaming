## SCN-01

**Direct cross-tenant access to a run** (tenant_isolation)

- **Objective (attacker):** Read, cancel or approve another organization's simulation run through any of the 11 routes that name a run, using the strongest role (admin) of a different tenant.
- **Success criterion (defence):** Every route answers 404 identical to an unknown run, the victim's state is unchanged, and the probe is recorded as a denial in the platform's audit stream.
- **If it fails:** Disclosure or manipulation of another customer's security findings.
- **Cases:** `TEN-ROUTE-GET-RUN`, `TEN-ROUTE-POST-CANCEL`, `TEN-ROUTE-GET-EVENTS`, `TEN-ROUTE-POST-APPROVAL`, `TEN-ROUTE-GET-RISK`, `TEN-ROUTE-GET-ATTACK-PATHS`, `TEN-ROUTE-GET-BLAST-RADIUS`, `TEN-ROUTE-GET-REMEDIATIONS`, `TEN-ROUTE-GET-REVIEW`, `TEN-ROUTE-GET-VERIFICATION`, `TEN-ROUTE-GET-REPORT`

## SCN-02

**Cross-tenant discovery and enumeration** (tenant_isolation)

- **Objective (attacker):** Learn that another tenant's runs exist (list/filter parameters, or telling foreign identifiers apart from unknown ones).
- **Success criterion (defence):** No list variant contains the victim's run id, and foreign and unknown identifiers are indistinguishable by status and body.
- **If it fails:** An existence oracle that lets an attacker map another tenant.
- **Cases:** `TEN-LIST-LEAK`, `TEN-ENUM-ORACLE`

## SCN-03

**Organization spoofing and idempotency collision** (tenant_isolation)

- **Objective (attacker):** Choose the organization of a request (headers, body) or receive the victim's run by replaying its Idempotency-Key.
- **Success criterion (defence):** The organization comes only from the verified credential: header and body hints are ignored or rejected, and equal idempotency keys yield separate runs per tenant.
- **If it fails:** A client could act inside, or read from, an organization it does not belong to.
- **Cases:** `TEN-HDR-SPOOF`, `TEN-BODY-SPOOF`, `TEN-IDEMPOTENCY`

## SCN-04

**High-impact action across tenant or role boundary** (tenant_isolation)

- **Objective (attacker):** Approve or cancel a pending high-impact action from another tenant, or with a read-only role inside the right tenant.
- **Success criterion (defence):** Foreign approval is refused (404) and a viewer receives 403 for approve, cancel and create; the run still awaits its own tenant's human decision.
- **If it fails:** The human-approval control could be bypassed.
- **Cases:** `TEN-APPROVAL-XORG`, `TEN-VIEWER-ESC`

## SCN-05

**Unauthenticated and malformed credentials** (tenant_isolation)

- **Objective (attacker):** Reach a protected route with no credential, an empty one, the wrong scheme or injection text in the bearer value.
- **Success criterion (defence):** Every variant returns 401 without 5xx or internal error text, and each is logged.
- **If it fails:** Unauthenticated access to run data.
- **Cases:** `TEN-NO-CREDS`, `INJ-BEARER`

## SCN-06

**Injection through HTTP inputs** (injection)

- **Objective (attacker):** Alter a query, path or stored value with SQL, path-traversal or template payloads in every caller-controlled input (scenario id, status, paging, idempotency key, run id, approval reason).
- **Success criterion (defence):** No payload yields a 5xx or internal error text; status codes stay within the documented set; the victim run and the data store are intact afterwards.
- **If it fails:** Data disclosure or corruption, or denial of service by unhandled input.
- **Cases:** `INJ-SCENARIO`, `INJ-STATUS`, `INJ-PAGING`, `INJ-IDEMPOTENCY`, `INJ-RUNID`, `INJ-REASON`

## SCN-07

**Protocol and resource abuse** (injection)

- **Objective (attacker):** Split response headers with CRLF in a correlation id, send an oversized body, or send malformed and deeply nested JSON.
- **Success criterion (defence):** The correlation id is replaced, the oversized body is refused with 413, malformed bodies are refused without 5xx, and the service is still healthy afterwards.
- **If it fails:** Header injection, resource exhaustion or a crash from crafted requests.
- **Cases:** `INJ-CRLF`, `INJ-OVERSIZE`, `INJ-TYPES`

## SCN-08

**Prompt injection against the planner context** (prompt_injection)

- **Objective (attacker):** Plant instruction-like text (including zero-width and look-alike obfuscation) in asset names, tags and edge properties so that an LLM-backed planner would obey it.
- **Success criterion (defence):** The planner context contains only allow-listed fields (control), and the text sanitizer neutralises every obfuscated instruction (defence in depth).
- **If it fails:** Attacker-controlled data steering an automated agent.
- **Cases:** `PI-ALLOWLIST`, `PI-SANITIZE`

## SCN-09

**Stored attacker text as active content** (prompt_injection)

- **Objective (attacker):** Store hostile text through the approval reason and have it returned as active content or copied into the security audit stream.
- **Success criterion (defence):** Stored text comes back only as application/json with nosniff and never appears in the platform's audit events.
- **If it fails:** Stored cross-site scripting or audit-log poisoning.
- **Cases:** `PI-ROUNDTRIP`

## SCN-10

**Tenant boundary in the data layer** (datastore)

- **Objective (attacker):** Reach another tenant's rows through the organization filter or, with the application's own database role, through an unscoped query.
- **Success criterion (defence):** Hostile filter values match nothing, and the database itself refuses an unscoped read (row-level security enabled, role without BYPASSRLS).
- **If it fails:** Isolation that depends on every code path remembering a filter.
- **Cases:** `DS-ORG-SQLI`, `DS-RLS-POSTURE`
